# DaggerheartGM

A GM tool for the Daggerheart tabletop RPG.

## Architecture

**UI color system:** Semantic game signals (Hope, HP, **magic** / spellcast & domains, sources, etc.) vs. neutral **theme chrome** are documented in **`docs/visual-language.md`**. Chrome is a fixed dark palette driven by CSS custom properties on `:root` and Tailwind tokens (`bg-dh-surface`, `text-dh-muted`, …) defined in `src/input.css`.

Express.js server serving a React SPA built from `src/client/`. **SRD feature mechanics** are implemented in **`src/features-v2/`** (declarative engine + per-collection modules); see **`docs/feature-authoring-guide.md`**. Authentication is handled by Firebase (**email/password** and **Google Sign-In**; same email can use either after **account linking** in Firebase — see **GCP / Firebase Setup**). Data persistence is backed by Postgres via Supabase. Client-side routing uses the History API (`src/client/lib/router.js`) so the browser back/forward buttons work across all views. The nav bar always renders, even for anonymous visitors — Sign In / Sign Up buttons replace the user menu and redirect to `/?authMode=signin|signup&returnTo=<path>`. The home route (`/`) shows a marketing hero + `AuthLanding` plus an auto-rotating feature carousel and screenshot series (`HomeFeatureShots`, last shot is live Public Games table cards) for anonymous visitors, or `HomeAuthenticated` (My Tables: Owner / Player / Public columns with 16:9 cards wrapping 2–3 across inside each section + My Library) for signed-in users. The **Library** (`/library/**`) is browsable without signing in — reads use `optionalAuth` and anonymous requests only ever see SRD/Public content; clicking New / Clone / Add to Table while signed out redirects to sign-in instead of performing the action. The Library opens on **`/library/all`** by default (bare `/library` resolves to the merged **All** SRD browse tab; per-collection tabs use `/library/:collection`). `GET /api/data/library-all` returns paginated rows from all unified SRD collections **plus** a **`features`** branch (V2 feature catalog from `src/features-v2/generated/feature-catalog.json`, generated by `npm run gen:feature-catalog`) when **Include SRD** is on; `featScope` query params filter that branch. When tier, level, namespaced type, or feat-scope filters are set, only collection branches those filters apply to are queried (see `shouldIncludeLibraryAllBranch` in `src/library-all-branch-opts.js`). At most one of those structural dimensions is stored at a time in shared library filters (`normalizeSharedStructuralExclusivity` in `src/client/lib/library-shared-filters.js`). `GET /api/data/features` lists the same catalog (read-only; not in Postgres). `GET /api/data/library-all-counts` returns per-collection counts without fetching rows (`countsByCollection` includes `features` when SRD is included). Game tables use **`/table/:tableId`** (and **`/table/:tableId/:collection/:id`** for item modals); legacy **`/gm-table/...`** URLs redirect to the canonical form. Four simple public static pages — **`/terms`**, **`/privacy`**, **`/support`**, **`/cookies`** (Terms of Service, Privacy Policy, Support/Contact, Cookie Policy; `src/client/components/legal/`) — require no auth and are linked from the single-row **`Footer.jsx`** rendered at the bottom of the anonymous home and `HomeAuthenticated`. Item detail modals also use `/library/:tab/:id`. **Multi-table support**: each owned table is a row in `table_state` (often the user’s first table uses id = Firebase uid; additional tables use UUIDs from `POST /api/my-tables`). `GET /api/my-rooms` returns `[{ tableId, gmUid, gmName, tableName }]` so invited players open the correct table. Table URLs are shareable with players; the GM manages which emails can join via "Manage Invited Players".

Data loading is **lazy and per-collection**: on sign-in the app renders immediately; `table_state` and admin status load in the background. Every **SRD reference collection** in the Library (abilities, ancestries, armor, adversaries, beastforms, classes, communities, consumables, domains, environments, items, subclasses, weapons) **plus** a dedicated **Features** tab (V2 mechanics catalog) is fetched on demand via `LibraryView`'s `useCollectionSearch` (per tab) or **`useLibraryAllSearch`** for the **All** tab, with default sources **Mine + SRD** (search text and source filter share library-wide keys `dh_library_search_query` and `dh_library_includes_sources`; tier, level, typed filters, sort, Include Scaled, and **feat scope** share **`dh_library_shared_filters_v2`** across SRD tabs and All — same scope as search/source). The Library **sidebar** hides Characters and Adventures, but those routes remain valid (deep links, Game Table pickers). Scenes, adventures, and characters load when the user navigates to those tabs or opens the Add Scene/Adventure/Character picker on the Game Table. The `GET /api/data/:collection` endpoint uses a **unified query** over `items` + `external_item_cache` for each unified SRD collection — no live external API calls. **All** SRD library tabs support **Clone to My Library** and **New** for user-owned rows; collections without a dedicated form (weapons, abilities, classes, etc.) use `GenericSrdLibraryForm.jsx` in `ItemDetailModal` (`name` + `description` + tier or level + images + optional full JSON). `POST /api/data/:collection/clone` rehydrates SRD sources from `external_item_cache` when cloning so the saved copy includes full JSON (e.g. images). **All** SRD JSON is loaded into the cache at server startup (`loadSrdIntoDb`). Scene expansion uses a batch `POST /api/data/resolve` call (with `adopt: true`) to look up referenced IDs, auto-cloning any non-own items into the user's library. The resolve endpoint falls back to `external_item_cache` or the SRD sub-application for IDs not in the user's DB. **Image optimization**: to avoid slow saves when scenes contain large base64 images, the client strips `imageUrl` and `_additionalImages` from normal PUT payloads; the server merges incoming data while preserving image fields. Image changes (AI generate, import) use a dedicated `PUT /api/data/:collection/:id/image` endpoint.

**Shared collection search**: a `useCollectionSearch` hook (`src/client/lib/useCollectionSearch.js`) encapsulates fetch/filter logic and is used by `LibraryView`, `AddToTableModal`, `FeatureLibrary`, and `ExperienceLibrary`. Per-tab defaults for the Library live in `src/client/lib/library-filter-config.js` (secondary filters such as ability domain / spell level, weapon slot + physical/magical, etc.). Source, Tier (or Level for abilities), Role/Type, optional second type (`type2`), and **sort** (popularity, name, type, source, tier). For adversaries, when exactly one tier is selected, an "Include Scaled" checkbox lets you include lower-tier adversaries; those are scaled up to the selected tier using RightKnight guide rules and displayed with "[Scaled]" prepended to their names. On the main Library (including All), tier/level/typed filters and sort persist in **`dh_library_shared_filters_v2`** alongside library-wide `dh_library_search_query` and `dh_library_includes_sources`; modal sidebars (`FeatureLibrary`, `ExperienceLibrary`) still use their own `dh_featureLibraryFilters` / `dh_experienceLibraryFilters` keys. A `CollectionFilters` component renders two variants: `bar` (horizontal, LibraryView) and `panel` (stacked, used in Add to Table modal and Feature/Experience Library). A virtualized grid (`@tanstack/react-virtual`) renders `ItemCard`s with infinite scroll via `loadMore` for SRD unified tabs. Card width/height sliders persist per signed-in user and library tab in `user_preferences` via `GET`/`PUT /api/me/preferences` (`libraryCardDimensions`), with localStorage as a write-through cache (`src/client/lib/library-card-dimensions.js`); short heights hide the preview pane; maximum height matches the visible grid scrollport (about one full row per screen). Item titles are centered between tier and actions. Scenes, Adventures, and Characters use a non-virtualized flex-wrap layout.

**Popularity tracking**: clone and play actions are recorded in `item_popularity` (one row per user per item per action). Counts are computed via subquery. Community items (SRD, public, mirrors) are sorted by popularity descending by default. A flame badge appears on cards with popularity > 0.

**Characters collection**: Characters are a fifth Library tab and collection. The character builder uses `CharacterForm.jsx` (controlled-mode form with identity, class, subclass, **declarative editor cards** after Subclass when a feature defines **`cards`** with **`placement: 'editor'`** — e.g. Beastbound **Companion** via `collectEditorCardsForCharacter` + `DeclarativeSchemaEditorCard` + JSON Schema), ancestry, community, traits, equipment, experiences, domain cards, advancements, and background sections), `character-calc.js` (pure utilities: `recomputeCharacter`, `tierFromLevel`, `computeTraits`, `computeMaxHp`, `computeMaxStress`, `computeEvasion`, `computeProficiency`, `resolveArmor`, `resolveWeapon`, `collectAbilityIds`, `computeWeaponModifiers` — parses SRD weapon feature text for stat-modifying properties like Cumbersome −1 Finesse, Heavy −1 Evasion, Protective +N Armor Score, etc., and applies them to the character's computed stats; stores `weaponMods` on the character for amber-highlighted display indicators), and `useCharacterSrdData.js` (React hook that fetches and caches SRD collections for the builder). **Build with AI** (`POST /api/character-ai-build`, `src/llm-character-builder.js`) now uses a legality-first staged OpenAI loop: the model picks a class package from a compact catalog, calls `fetch_character_build_profile` to get only legal domain cards and advancement options, calls `validate_character_build_draft`, and only then returns final JSON. `src/character-ai-resolve.js` resolves names to ids and optional `sheetDisplayNames` for weapons/domain cards. Optional `AI_USAGE_DEBUG=1` logs token usage through `src/ai-usage-log.js`; `CHARACTER_AI_DEBUG=1` adds per-turn builder diagnostics for this legality-first character flow. Shared display components (`CharacterDisplay.jsx`: `CharacterIdentityHeader` — shows a small circular portrait from `el.imageUrl` when set, falling back to the User icon; `CharacterTraitGrid`, `CharacterDefenseRow`, `CharacterWeaponList`, `CharacterFeatureList`, `CharacterAbilityList`, `CharacterExperiences`, `CharacterInventory`, `DeclarativeSchemaSheetCard`, `CharacterDetailPane`) are used by `ItemDetailModal` and `CharacterHoverCard`. Beastbound companions render **inside** the main sheet (declarative cards between Actions and Features) and on the sidebar card (companion stress); there is no separate companion column on the hover overlay. `DaggerstackImport.jsx` is a reusable Daggerstack import component used by both `ItemPickerModal` (inline compact mode for Game Table) and `LibraryView`. Characters are managed through the Library picker — the inline character dialog was removed from GMTableView.

**Characters by reference and table ownership**: On the Game Table, characters are stored by reference. The persisted `table_state.elements` entry for a character contains only `CHARACTER_PERSIST_KEYS` (`CHARACTER_RUNTIME_KEYS` + `id` + `name`). All other character fields (weapons, traits, features, tier, etc.) are resolved from the character library at read time. **Server-side resolution** (`resolveCharacterElements` in `db.js`) runs whenever `table_state` is read. Each character belongs to exactly **one table**: the `items` table has a `table_id` column stamped on every character row (migration 037), and every write to `PUT /api/data/characters` requires `_tableId` in the body + `resolveTableAccess` (owner or invited player). The canonical write path (`upsertCharacterForTable`) does a user-agnostic UPDATE/INSERT — player saves update the GM's existing row rather than creating a shadow row under the player's uid. A partial unique index (`items_characters_id_unique`, migration 038) enforces one row per character id across all users, permanently closing the "diverging shadow rows" production bug. The Library no longer has a Characters tab; characters live entirely inside tables. **Phase 1 server-authoritative state**: all table mutations (element updates, fear, map changes, etc.) go through `POST /api/room/my/op` which writes to the DB and notifies the subscription manager; the manager pushes a full resolved `table_state` snapshot to all connected SSE clients. The old client-side `resolvedActiveElements` useMemo, `saveTableState` debounce, and `broadcastingUpdate*` wrapper functions have been removed. **Live character updates**: when a character is saved via `PUT /api/data/characters`, the server notifies the `table_state` subscription for that table, so all clients receive a fresh resolved snapshot automatically. The character pencil edit button on the Game Table goes directly to "edit library original" mode (no EditChoiceDialog) since editing a table copy is meaningless in the by-reference model. Daggerstack re-sync also saves the synced data to the library.

**Library Maps** (`collection: 'maps'`) — first-class library items (Mine + DT catalog + Public). Art URL and name/artist/size are shared; cameras, overlays, dressing, and `shareWithPlayers` stay table-local after add (`libraryMapId` + `librarySyncImage` on each `table_state.maps[]` row). Library Map cards fill leftover preview with the art (shrinking down to square before truncating content below); maps with 2+ cameras also show a centered horizontal row of camera tiles under the image. Library tab **Maps** sits just after Scenes. GM **Add Map** is on the hovering map-tile overlay (`MapCameraPicker`), not a strip above the map — it opens `ItemPickerModal` multi-select. Create New stubs the table + library then opens `MapForm` / `MapTableEditor`. Scenes store `libraryMapId` and a capture-time camera/dressing snapshot; Load Scene uses current library art. Publishing a Scene is blocked until referenced maps are public.

**Battle maps (multi-map + views)** — `table_state` stores `maps` (with `shareWithPlayers`, optional `libraryMapId` / `librarySyncImage`, and optional `artist` / `artistUrl` for a bottom-right **Map by** credit), `mapViews` (named cameras per map with `broadcastToPlayers`, `locked`), and `gmActiveViewId`. Each view persists framing as legacy `mapViewZoomRatio` / `mapViewPanNorm` plus preferred **`mapViewVisibleNorm`** (`{ x, y, w, h }` in 0–1 inner-map space) so the same shared region fits on any screen without showing extra map outside the GM’s frame. `attachDerivedMapConfig` in `src/client/lib/map-table-state.js` derives a legacy-shaped `mapConfig` for the GM’s active view. Players resolve framing via `deriveMapConfigForViewId` and a locally selected broadcast view, or free pan/zoom on the shared map tile (client `localStorage`). Tokens may carry `mapId` and optional `altitude` (feet, implicit default 0); `map-range.js` only measures range between tokens on the same map, combining planar nearest-edge distance with Δaltitude as a sphere (`tokenDistanceFt` trailing altitude args). `map-range.js` is the single canonical distance implementation shared by the client range helpers, `BattleMap.jsx`'s bullseye/range-band highlighting, and `src/features-v2/engine/table.js`'s `rangeFrom`/`rangeBetween` (V2 engine hooks). Historical migrations `020`–`022` introduced then removed a separate `personal_map_cameras` table (`023_drop_personal_map_cameras.sql`).

**Daggerstack character sync**: GM Table characters can be linked to a [Daggerstack.com](https://daggerstack.com) character sheet. The `DaggerstackImport` component provides URL, email, and password inputs. On sync, the server calls `POST /api/daggerstack/sync` → `src/daggerstack-sync.js`, which authenticates via Daggerstack's Supabase backend, fetches the character row, and resolves class/subclass/ancestry/community/armor/weapon UUIDs against local SRD data (via `data/daggerstack-uuid-map.json`). The sync output now includes SRD reference IDs for resolved entities. Resolved fields include evasion (class base + armor/ancestry modifiers), armor score + thresholds, all traits, weapons, inventory, and features. Credentials are stored on the character element and used for later re-sync. Re-sync also saves to the library so changes propagate to the table via the by-reference resolution layer. Hovering a character card shows a `CharacterHoverCard` overlay to the right of the Characters panel with a full character sheet. The small card also shows an Armor `CheckboxTrack` + Evasion badge when populated. The UUID map is generated by `scripts/refresh-daggerstack-uuids.js` and refreshed nightly at 4 AM (also runnable via `npm run refresh:daggerstack`). `table-ops.js` `CHARACTER_RUNTIME_KEYS` defines the table-local fields preserved during character resolution.

The nav bar user menu (click your name/email) provides a **Feature authoring guide** (loads `docs/feature-authoring-guide.md` via `GET /api/docs/feature-authoring-guide` into a split-pane modal), **Enable onboarding** (clears onboarding tips such as the character editor first-time banner), Export JSON, Import JSON, and Sign Out. **V2 SRD feature migration** is tracked in **GitHub Issues** (label `v2-migration`) when `GITHUB_TOKEN` + GitHub `origin` are set — see `scripts/lib/github-v2-tracker.mjs`, `npm run setup:v2-migration-labels`, `npm run v2:sync-tracker-md` (regenerates `docs/v2-migration-tracker-snapshot.md`). Implementation agents claim **`abilities/` → `beastforms/` → `items/` → `consumables/`** while any earlier collection has `Unclaimed` rows; **`subclasses/`** does **not** block that chain; then tier/priority-domain order within **abilities** — see `docs/agent-prompts/implementation-agent.md`; **Human approval queue** (`docs/agent-prompts/human-approval-queue-agent.md`, magic phrase in `.cursor/rules/v2-agents.mdc`) processes **Blocked/API** (design) and **Awaiting Human** (fix) rows in Cursor chat (`npm run v2:human-queue`; **reject** on fix rows → **`Needs Fix`** + **Val Notes**); **V2 UI integration backlog** (Game Table wiring); **Phase 0** persistence (`featureState` runtime keys + handoff doc) is described in `docs/v2-ui-integration-phase1-handoff.md`; **Phases 2–3** (V2 banner bridge: `src/client/lib/v2-action-loop-bridge.js`, `DiceRoller` / `GMTableView`) are summarized in `docs/v2-ui-integration-phase3-handoff.md`; **Phase 4** (cross-sheet chips, token-move hooks, session/scene lifecycle) is in `docs/v2-ui-integration-phase4-handoff.md`; **V1→V2 Game Table cutover** remaining backlog is in `docs/v2-game-table-cutover-remaining.md` (north star: `docs/v2-game-table-polestar.md`); **Phase B** (bridge hardening: `partitionV2BannerChipMutations` + `postBannerAddDamage` / `postBannerRerollDie`, V2 review `isSelect` / `selectTargets` pickers in `DiceRoller`) is **done** — handoff `docs/v2-ui-integration-phaseB-handoff.md`; Rally banner merge + session/scene Rally clear remain deferred; **completed** API resolutions are append-only in `docs/v2-blocked-resolutions-done.md`. The V2 engine (`src/features-v2/engine/table.js`) exposes **`table.action.useArmorByTargetId`**, per-damage-effect **`useArmor`**, **`table.me.activeModifiers`** with **`addActiveModifier`/`removeActiveModifier`** (mutation types **`appendActiveModifier`**/**`removeActiveModifier`**), and **`table.action.reduceIncomingPhysicalSeverityBySteps`** for incoming physical threshold reduction (see Feature Authoring Guide §C.3). **`collectChipsForOtherCharacterSheets`** in **`chip-system.js`** collects opt-in chips (**showOnOtherSheets**) from other PCs’ features for display on the open character sheet (see **`CharacterExperiences`** **`crossSheetChips`**). The client helper **`applyV2ActiveModifierMutations`** in `table-ops.js` merges those modifier mutations onto character elements in **`activeElements`**. **`dispatchStateChangeHooks`** runs **`hooks.onStateChange`** after external mutation batches (with **`table.mutationBatch`**); **`dispatchSceneEndHooks`** runs **`hooks.onSceneEnd`** when the host signals a scene end. Full Game Table wiring from roll metadata and from armor/rest/scene mutations is optional follow-up work.

### SRD Content

SRD content is served from the `daggerheart-srd` git submodule via the `src/srd/` sub-application (public `/api/srd/:collection`). All 13 SRD collections are also **upserted into `external_item_cache`** on startup via `loadSrdIntoDb` so authenticated `GET /api/data/:collection` can merge user items with SRD in one query. In-memory and DB copies stay in sync when the SRD hash changes. DT catalog scenes are **not** in the parser `COLLECTION_NAMES`. `loadDtScenesIntoDb` (`src/dt-scenes-loader.js`) upserts them on startup from `data/dt-scenes/` (Crossroads Ambush `srd-scene-crossroads-ambush`, Cross the Raging River `srd-scene-cross-the-raging-river`) into `external_item_cache` (`source='dt'`, `collection='scenes'`), and un-publishes the original UUID items rows. `loadDtMapsIntoDb` (`src/dt-maps-loader.js`) upserts extracted maps (`srd-map-crossroads`, `srd-map-raging-river`) as `collection='maps'`. `npm run generate:srd-scenes` runs both paths (requires only `DATABASE_URL`). The legacy `--from-environments` mode restores the old 17 auto-generated environment scenes with SVG map uploads (requires `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY`). With `includeSrd` on (official catalog), `GET /api/data/scenes` and Library All include DT cache rows; Scenes Include labels them **DT** and cards show the DT badge. Admin edits stamp `_adminEditedAt` so `loadSrdIntoDb` / re-seed skip those rows unless `--force`.

The `/api/srd` routes are public (no auth). To update SRD content to a newer upstream version:

```bash
cd daggerheart-srd && git pull && cd ..
git add daggerheart-srd && git commit -m "Update daggerheart-srd submodule"
```

SRD rows live in `external_item_cache`. User-published community items appear under **Include Public**. External SRD items are read-only in their source form; use "Clone to My Library" or the in-context "Edit Copy" flow to make an editable copy. **Adding any item to the Game Table automatically clones it to your library** (finding an existing auto-clone if one already exists), so your library reflects everything you've actually used at the table.

A **compact/spacious view toggle** (grid icon in the header) switches between a spacious 3-column card layout and a dense 7-column layout. Compact mode hides the banner image and shows a small bottom-right thumbnail that expands on hover. The choice is persisted in `localStorage` under `libraryViewMode`.

### Built-In Dice System

The **Game Table** tab layout: a **Characters panel** (left sidebar, `w-56`) with a dedicated "+ Add Character" button and character cards; a **center column** (`flex-1`) with a compact **Action Log and Dice Roller strip** (`ActionLog.jsx`) above the **Battle Map** (`BattleMap.jsx`); an **Encounter panel** (right sidebar, `w-56`, GM only) with a sticky strip (Session/Rest, **Call for Reaction**, Fear, GM Moves) and a scroll area with sectioned **Notes**, **Countdowns** (`SessionCountdownsPanel.jsx` section layout — name + value on each card; hover opens the shared left-of-aside overlay with properties + DC chart; GM edits via `SessionCountdownEditorModal.jsx`, including the same dynamic DC outcome reference chart), **Environments**, and **Adversaries** (BP Budget lives in the Adversaries section). Each section title row has a compact **+ Add** control on the right (opens the picker or creates a blank note where applicable). When AI is enabled, an **Encounter builder** strip at the bottom runs `postEncounterAiBuild` / `POST /api/encounter-ai-build` only (no in-panel adversary/environment concept tabs).

The "+ Add Character" button in the Characters panel opens an **`ItemPickerModal`** for the Characters collection — characters are created and edited in the Library, then added to the table from the picker. Characters are GM-side party tracking cards stored as `elementType: 'character'` entries in `activeElements` (no separate DB collection). Each character has a name, player name, **tier** (1–4, default 1; selected via the shared `TierSelector` component), Hope counter (±buttons), HP track, Stress track, and a Tag-gated multi-entry conditions editor (`ConditionsEditor`; shared per-table `conditionsHistory` suggestions). Beastbound Rangers show a companion stress block on the card (clearly delineated) with the same conditions editor for `companion.conditions`, and companion map-token pins get the same Tag+box. A tier badge (`T{n}`) is displayed on each character card header. The highest character tier (`partyTier`) is used as the comparison basis for the "lower-tier adversary" BP budget auto-modifier. Character cards use sky-blue styling to distinguish them from adversaries (dark) and environments (emerald). The pencil icon reopens the character picker pre-filled for mid-session edits. Clear Table preserves character cards — only adversaries and environments are removed.

**Multi-player support**: GMs generate a reusable `/join/:token` invite link in the Players panel (Invite Link + Joined roster). Players sign in via that link (their verified email is appended to `playerEmails`) and see nav tabs for each table they're invited to (`GET /api/my-rooms`). **Public tables**: the GM can check **Public table** under the map title gear (`set-table-public` / `items.is_public`). Anyone with the URL can spectate (signed-out included) via `GET /api/data/table_state?tableId=` (player redaction) and `GET /api/room/:tableId/public-stream`; they cannot move tokens, roll, add characters, or edit. The homepage Public column (signed-in) and the anonymous **Public Games** marketing shot list recently updated public tables (`GET /api/public-tables`, `optionalAuth`). If spectators are connected, **Audience (N online)** appears under Joined. Players can **Leave table** (confirm dialog); the GM can kick a player from the Joined roster. **Homepage cards update in real time** via `GET /api/home/stream` (SSE, token query param, subscribed while `route.view === 'home'`): pushes full card DTO snapshots on `home_owned`, `home_invited`, and `home_public` channels when card-visible fields change (name, GM name, roster, or preview PNG — token drags do not fan out); `toTableCardDto` appends `?v=<tablePreviewAt>` to preview URLs so the browser re-fetches the composite PNG after each screenshot regeneration. Real-time sync uses **Server-Sent Events (SSE)**: `GET /api/room/my/players` (with `?tableId=`, **owner-only**) keeps the GM updated on who is connected to that table; `GET /api/room/:tableId/stream` streams table state and dice roll events to invited players. **Operational sync**: each GM mutation (HP toggle, fear change, element add/remove, etc.) broadcasts a lightweight `table-op` SSE event via `POST /api/room/my/op` so other clients see changes instantly. The debounced table_state save (2s) handles DB persistence and provides consistency repair for any lost ops. `CLIENT_ID` (stable per-session UUID) tags both saves and ops for self-echo skip. When the GM rolls dice, 3D dice animations play on all screens simultaneously; the GM acknowledges the roll (via `POST /api/room/my/banner-ack`), which applies side effects on all clients. **Banner queue** uses a Postgres LISTEN/NOTIFY subscription (`src/subscriptions.js`): a DB trigger fires on every `dice_rolls` mutation; `SubscriptionManager` re-queries pending banners and pushes the authoritative list to all connected clients as a `banners` SSE channel event — eliminating the old delta-accumulation pattern (`playerDiceRollQueue`, `pending-banners` event). The GM can assign characters to specific players (`assignedPlayerUid`); assigned players can edit their own character's resources (HP, stress, hope) while all other table content is read-only for players.
- **Battle Map** (center) — a custom, purpose-built battle map (`BattleMap.jsx`). The GM can upload a map image (or use a blank area) and configure its real-world size (1–3000', default 250'). A hanging **table-name inset** (gear + title; when editing: name, **Public table** checkbox, Delete stacked vertically) sits at the top-center of the map viewport. The on-map **camera picker** (`MapCameraPicker`, left-aligned with the Map Zoom / Camera Zoom title) shows the current camera chip and expands on hover into a Maps / Cameras overlay (current camera last in a right-justified ribbon so it stays under the cursor; current map first; 25%-of-tile gap between the Maps column and Cameras) with per-row map titles, camera titles above the tiles, and size/artist/URL beside each map. When an artist is set, a bottom-right **Map by** inset appears (`MapArtistCredit`) and becomes a new-window link if a URL is set. Character and adversary tokens (5×5' circles by default) can be dragged onto the map. **Per-token size multipliers**: a character/adversary (or a Beastbound companion) can have a library-scoped `tokenSizeWidth`/`tokenSizeLength`/`tokenSizeLinked` (edited via the "Battle map token size" row in `CharacterForm`/`AdversaryForm`, or the companion's own editor card) that scales its token to a non-default width/length; range/adjacency math accounts for this via true ellipse projection (`src/client/lib/token-size.js` + `map-range.js`) so a token's effective "reach" scales with its footprint everywhere distance is computed (default 1×/1× tokens are numerically unaffected). **Token altitude**: placed tokens may carry `altitude` (feet, implicit default 0, can be negative). A floating control to the left of the token (`TokenAltitudeControl` in `BattleMap.jsx`, helpers in `src/client/lib/token-altitude.js`) draws a stem from the token center at map scale (1′ of altitude = 1′ on the map; positive up the screen; colored to match the token's ally/role color (not the range-band glow)) with a compact always-on value at the tip; the interactive control appears beside the token on hover for anyone who can move that token (drag vertically in 5' steps at a rate that matches stem length at the current zoom, so the number and stem grow together while the control stays next to the token; double-click resets to ground). Range is a sphere: planar nearest-edge plus Δaltitude, so a token at Melee on the ground can be Far from one 60' above. Hovering a token shows a `ΔN'` chip on other in-band tokens whose altitude differs. Returning a token to the tray clears altitude. Unplaced tokens live in side trays outside the scroll area (trays always show tokens at the uniform baseline size, regardless of library size). The GM's right tray always reserves the Place all / Return all icon row above the GM token (disabled when empty) so that token does not shift when the first adversary is added. **GM — Cancel all**: in the left character tray, a control above the hide/show and clear 3D dice buttons dismisses every pending roll banner at once (confirm; same as Cancel on each banner, no mechanical effects). The map scales so tokens are always at least 44px (touch-friendly for iPad). The map viewport does not use native scrolling; pan and display zoom use the keyboard, scroll wheel (⌘/Ctrl+wheel to zoom toward the cursor), and right-drag (feet and token positions are unchanged). **ZOOM TO** (underlined group: **Actors** / **Party** / **Adversaries** — Focus / Users / Swords) sits at the left of the map/view strip; **SCENE** (**Create** / **Add**) sits on the right. Map and camera strip tiles show small presence chips for actors in that thumb's viewport; same-type adversaries collapse to one marker (`LAx2`) via `src/client/lib/map-strip-token-proxies.js`. Actors fits every placed token, Party fits characters and companions, Adversaries fits adversary tokens — each enabled when at least one matching token is on the map. The map-draw toolbar has a circle-slash clear control on the far left and a right-aligned **Zoom** bank (Lock, then Actors / PCs / Adversaries). The **GM** persists framing via `set-map-view` (`mapViewZoomRatio` / `mapViewPanNorm` / `mapViewVisibleNorm` in `table_state`). **Players** use the same interactions when their map allows pan/zoom; they follow GM updates until they move the view locally, then the strip highlights and **Follow GM** reapplies the synced view. Each token has a black border decorated with small SVG dot indicators showing resource state: red (HP damage/remaining), orange (Stress), cyan (Armor — characters only). Applied conditions appear as an extra group on that same ring, using the same pip size as HP/Stress/Armor, with a text glyph assigned by condition name (`src/client/lib/condition-symbols.js`) so the same condition shares one icon on every token. The group is omitted when the token has no conditions so it takes no arc space. Hovering a mark shows an instant tooltip with the condition name. The same glyphs appear as left-hand icons on `ConditionsEditor` chips and suggestion dropdown rows. When `element.imageUrl` is set (adversary or character), tokens render a circular portrait photo instead of the letter abbreviation (`src/client/lib/token-abbrev.js` — adversaries drop a shared table-local name prefix so `Jagged Knife Hexer` / `Lieutenant` become `HE` / `LI` instead of both `JK`); dot ring, condition marks, and defeated overlays remain on top. Clicking a token pins a detail panel. If the element has an image, a small circular portrait appears in the header and clicking it opens the shared GMTableView lightbox. Players can only drag their own assigned character's token. Adversary tokens in the right tray are hidden from players (the GM can reveal them by dragging onto the map). **Placed image objects** (`elementType: 'mapImage'`): any table member can paste, drop, or click **Map Image…** (GM toolbar) / ImageIcon (player button) to open `MapImageQuickPickMenu` (`src/client/components/modals/MapImageQuickPickMenu.jsx`) which offers New Map, Replace Map, New Image on Map, Import Tools, and — when an editable character or adversary modal is open — **"Add to '[Name]'"** (sets `imageUrl` if empty, else appends to `_additionalImages`, mirroring `ImageEditor.handleAddUrl`; auto-saves via the 800ms debounce). Map images are uploaded to **Supabase Storage** (`whiteboard-assets` bucket, `map-images/` prefix) via `POST /api/room/my/map-image`. Without Supabase configured, the server returns a data URL directly (no error). Requires `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` for CDN hosting; otherwise data URLs are used automatically (see Supabase setup below). **Inline blobs never enter `table_state`**: pasting, dropping, or importing a map image (all paths funnel through `UnifiedImportModal`'s map branch → `onAddMapWithImage`) uploads the cropped/pasted image to Storage via `sendAddMapWithImage` in `app.jsx` *before* posting the `add-map` op, and `applyOpToTableState` in `server.js` runs a second, server-side upload guard (`src/server/map-storage.js`) on `add-map`/`set-map`/overlay ops and `mapImage` elements as defense in depth — this closes a bug where an inline data-URL map image bloated a table's `table_state` row to several MB and added multi-second latency to every op for that table. **Range band bullseye**: hovering anywhere over the map canvas shows a multi-ring SVG overlay of concentric Daggerheart range bands (Melee, Very Close, Close, Far, Very Far) centered on the cursor. Hovering over a token snaps the center to that token's center (and altitude). During a token drag, the bullseye freezes at the drag origin so range bands remain visible from the start point. Placed tokens receive a colored outer glow matching their current range band (sphere distance including altitude). Moving onto a token's altitude stem or control keeps that snap via an expanded hover zone.
- **Action Log and Dice Roller** (center, strip above battle map) — a compact history of rolls and action notifications for the current session; auto-scrolls to the newest entry. The expanded panel includes an in-panel dice roll builder (GM only, `ManualDiceBuilder.jsx`): a dedicated live-3D Duality preview (fixed Hope d12 + Fear d12 pair) next to a big checkbox (default off), a shared live-3D tray of the currently-selected d4/d6/d8/d10/d12/d20 dice (debounced rebuild, capped preview count, real DiceBox instances reusing the same colorset helpers as real rolls via `dice-color-groups.js`), and big per-size inputs with a dimmed/lit die-face glyph; Roll produces a banner for the GM to acknowledge. Short Rest and Long Rest open a wide **Rest banner** (1d4 + N Fear): each character chooses downtime moves from dropdowns (slot counts follow merged V2 rest stats — CONV-011); optional V2 **`placement: 'rest'`** chips (e.g. Potion of Stability) sit above the moves. GM can set any; players only their assigned character; when all are filled, Acknowledge adds Fear and refreshes rest-use features. **Call for Reaction** (Encounter panel, or a Zap on a character card) opens `ReactionCallModal` so the GM picks characters, a trait, and a Difficulty; that posts a pending **Reaction Roll** marquee (`ActionBanner`, `_reactionCall`). Each target (GM, or that character's assigned player) clicks **Proceed**, which reuses `handlePlayerOwnRoll` with `_isReaction` so preroll chips such as Elf Quick Reactions still apply; results fold into the marquee roster; the GM's single Acknowledge/Cancel dismisses the marquee and every correlated sub-roll. When a banner chip adds extra damage (e.g. Faun Kick), the banner updates in place and only the new dice animate, for a smooth transition on all clients.

Dice rolling requires no external service or credentials. Attack actions are always clickable:
- Clicking an action in the **GM Moves** overlay rolls server-side and briefly flashes green on success. Sections are sorted by Encounter-panel source order (environments, then adversaries); Fear Actions are preferred over Actions; adversary moves not in the current camera view sit in an **Off camera** fold.
- The **attack line** and **action-type attack features** on each adversary card also show a dice icon and roll when clicked

Rolls are processed by `POST /api/room/my/roll` (GM, body includes `tableId`) or `POST /api/room/:tableId/roll` (player). The server uses `crypto.randomInt` for tamper-proof dice and broadcasts results to all room clients via SSE. An in-memory ring buffer (last 50 rolls) is sent to late-joining players on connect.

**Weapon feature automation**: Character weapon rolls include `{FeatureName: description}` tags in the roll text. The server extracts tags and returns them in the response alongside dice results. The `ResultBanner` renders each tag as a compact pill. Features span five tiers of automation:
- **Passive stat mods** (Cumbersome, Heavy, Protective, Barrier, Brave, Double Duty, Paired) — applied at equip time via `computeWeaponModifiers`; no banner tag.
- **Roll construction** (Reliable +1, Sharpwing +Agility, Bonded +level) and **dice extensions** (Powerful/Massive `2dXkh`, Brutal `dX!`, Self-Correcting `dXm6`, Serrated `dXm8`) — modify the roll text before sending.
- **Post-roll effects** (Scary, Painful, Deadly, Burning, Reloading, Invigorating, Lifestealing) — auto-applied when the banner is dismissed.
- **Interactive UI** — **Quick** (second-target prompt after primary damage, marks 1 Stress), **Devastating** (toggle on weapon card for d20 damage, marks 1 Stress), **Lucky** (reroll button on Fear, marks 1 Stress), **Doubled Up** (secondary weapon damage to another Melee target after primary), **Pompous** (blocks rolling when Presence > 0 with an amber warning), **Bouncing** (looping multi-target phase after primary damage, each costs 1 Stress).
- **Virtual alternate weapon cards** (Phase 5) — **Versatile** shows an amber alternate-stat card with different Trait/Range/Damage; **Otherworldly** shows Physical and Magical variant cards, hiding the original; **Charged** shows an amber +1-die copy, disabled when Stress is maxed, marks 1 Stress on banner dismiss. **Action notification cards**: **Startling** shows a clickable Force Back card (1 Stress) that displays an amber notification banner without rolling dice. **Defensive reactions**: **Parry** intercepts damage application — a server roll is made, matching die values cancel attack dice, final damage is reduced. **Comprehensive reference**: see [`docs/srd-implementation.md`](docs/srd-implementation.md) for a full SRD implementation burndown including all 38 weapon features and their automation status.

### Adding to the Game Table

The Encounter panel uses a compact **+ Add** on each section title row (Notes, Countdowns, Environments, Adversaries) plus **Load Scene**. Adversary, Environment, and Scene pickers open **`ItemPickerModal`** in multi-select mode: click toggles a basket shown as removable footer chips (horizontally scrollable; adversaries have a 1–20 count), hover shows a right-hand library card preview, and **Add** appends the basket to the table (never clears the board). The Scene editor **Details** tab can author **Next Scenes** (`nextScenes: [{ id, name }]`); completing Load Scene writes that list onto `table_state` (replacing any previous list), and the Load Scene picker shows those scenes as one-click chips under the header. Selected scenes open **Add vs Replace** (`SceneAdoptDialog`); Replace clears the table then loads the first scene and appends the rest. The Scene editor uses the same multi-select picker for Environments and Adversaries, **# of PCs** and **Tier** dropdowns (stored as scene `partySize` / `partyTier`, default 4 PCs of Tier 1) for BP budget, the lower-tier modifier, and minion-group size (discarded when the scene is loaded onto a table — the live PC count and highest character tier are used instead), the same **Notes** click-to-edit flow (`EncounterNoteEditorModal`) as the Game Table, the same Encounter hover detail panels (`EncounterHoverOverlays.jsx` — note markdown, countdown properties + DC chart, and environment/adversary sheets on card hover; no Edit or dice in the Scene preview), and a **GM Moves** preview (`GmMovesPanel.jsx`) so you can see the scene’s Default Moves / adversary / environment board as it will appear on the table (hover descriptions only — no dice or Fear spend). Other pickers (`CollectionRefPicker`, `EnvironmentForm`) stay click-to-add. The modal uses `useCollectionSearch` + `CollectionFilters` (panel variant) with Source, Tier, Role/Type, and infinite scroll. Notes **+ Add** creates a blank table note and opens the note editor. Countdowns **+ Add** posts a `session-countdown-upsert` table op and opens the countdown editor (see `SessionCountdownsPanel.jsx` + `modals/SessionCountdownEditorModal.jsx`).

A **Capture Table** button (camera icon, disabled when the table is empty) opens a small dialog where you name and save the current table contents as a new **Scene** (capturing all adversaries and environments). After saving, the new scene is opened in the library.

### Environment — Potential Adversaries

Environments carry a structured `potential_adversaries` field: an array of `{ adversaryId?, name }` objects. SRD source strings keep official group shorthand (`Jagged Knife Bandits (Hexer, …)`); `parseSrdPotentialAdversaries` expands those short names (and standalone plurals like `Fallen Shock Troops`) to the real adversary id before the link is stored.

- **Linked reference** (`{ adversaryId, name }`): points to a real adversary in the library or SRD. Displays with a chain-link icon.
- **Placeholder** (`{ name }`): a named-only entry with no linked adversary yet. Displays with a dashed border.

In the environment edit form (`EnvironmentForm`), a **"Potential Adversaries"** section lets you:
- **Find & link**: opens the adversary picker (searches own, SRD, and public library adversaries).
- **Enter a placeholder**: type a name and press Add/Enter.
- **Link a placeholder later**: click the search icon on any placeholder to open the picker pre-filtered to that name.
- **Create from placeholder**: click the plus icon to instantly create a new adversary stub (inheriting the environment's tier), which replaces the placeholder with a linked reference.

SRD environments auto-populate linked references using deterministic SRD adversary IDs (`srd-adv-<slug>`). The `normalizePotentialAdversaries(raw)` helper (`src/client/lib/environment-potential-adversaries.js`, re-exported from `EnvironmentForm.jsx`) coerces any legacy string or empty value to the array format and is used throughout the display layer.

### Scene / Adventure Forms

Scenes can reference adversaries, environments, and **nested Scenes** (allowing reusable encounter building blocks). When creating or editing a Scene or Adventure, a bank of **"Add Adversary / Add Environment / Add Scene"** buttons appears via the `CollectionRefPicker` widget. Each button opens the same `ItemPickerModal`. All selected items appear in one combined list with type badges, quantity controls (for adversaries), and remove buttons. Pre-existing references are resolved on mount via `POST /api/data/resolve`.

**Circular reference prevention**: `SceneForm` validates nested scene selections at save time — if adding a scene would create a cycle (scene A → scene B → scene A), the save is blocked with an error. All expansion functions also pass a `visited` set to guard against cycles in stale data.

Nested scene chips display in **blue** on `ItemCard` in the Scenes library tab.

### Unified import (stat blocks, maps, notes)

GM sessions use **`UnifiedImportModal`** (`src/client/components/modals/UnifiedImportModal.jsx`) behind **`UnifiedImportProvider`** (`src/client/lib/unified-import-context.jsx`). In `app.jsx`, **`AiUiPreferenceProvider` wraps `UnifiedImportProvider`** so the modal (and embedded **Generate with AI** controls) receives the same AI visibility prefs as the rest of the app. Open from the nav **Import** button, the Library **Import** button, **drop** images on the app (outside import UI), **paste** images from the clipboard, or from the battle map **Upload** / drop when on the Game Table as GM.

**Flow**: load images (client-side page layout + optional **Crop…** via `PageLayoutPreviewModal`), merge OCR text with always-visible **Additional text**, choose type per slice (adversary / environment / map / note), preview and edit via `ImportPreviewCard`, then **Import**. On the Game Table, **Add to table** defaults on for adversaries, environments, maps, and notes. Server parsing uses `POST /api/import/parse` (OCR + `detectCollection()` with `src/import-type-hotwords.js` heuristics). Notes (and text-first adversary/environment refinement) use `POST /api/import/encounter-parse-text`.

### Markdown Support

All multi-line text fields support **GitHub Flavored Markdown** (GFM): bold, italic, bullet lists, numbered lists, blockquotes, inline code, and links. This applies to feature descriptions, adversary/environment descriptions, motives, and scene/adventure descriptions — for items of any origin (own, SRD, Reddit, Public, or created from scratch).

A `MarkdownHelpTooltip` icon (?) appears next to description and feature textareas in all edit forms. Hovering shows a compact cheat sheet and a link to the full GFM documentation.

**Rendering**: `FeatureDescription` renders feature text as markdown HTML with GM-trigger phrases (spend/mark fear, mark stress) and dice patterns (XdY+Z, e.g. 2d6+3) bolded as a post-processing step. Other multi-line text fields use the `MarkdownText` component (`src/client/lib/markdown.js`, `.dh-md` CSS class). Items truncated for compact display (card grid, GM sidebar) remain plain text to avoid jagged `line-clamp` truncation.

**OCR parsing**: when a Reddit stat block image is parsed, Strategy 1 of the text parser now preserves newlines and applies `formatListPatterns()` to auto-detect and convert d-table ranges (`1-2: Sugar Shrub. 3-4: Spiced Gravel.`) and concatenated numbered lists into proper markdown bullets. The LLM parser is similarly instructed to emit markdown for feature descriptions containing roll tables or lists.

### Item Detail and Editing

All item viewing and editing happens inside a single **`ItemDetailModal`** overlay — there are no separate view or edit pages.

- **Library**: Clicking any card (or "New") opens `ItemDetailModal`. Own items show a split pane: **live display preview** on the left (updates in real-time as you type), **edit form** on the right. Adversaries show a stacked **Feature + Experience Library** (tab switcher; experiences from matching adversaries); environments show a narrow **Feature Library** panel; characters use `CharacterForm` with `CharacterDisplay` in the preview. Changes **auto-save** after 800ms of inactivity (header shows status: Saving / Unsaved / Saved, and **Done** to close). First-time character editor can show a dismissible tip (new characters save once named). **Undo/redo** (Ctrl/Cmd+Z / Ctrl/Cmd+Shift+Z) are available for the full session. SRD/public items open display-only with a Clone action.
- **Game Table**: The pencil button on each card opens an `EditChoiceDialog` asking "Edit Table Copy" or "Edit Library Original", then opens `ItemDetailModal`. Copy mode auto-saves only in memory (preserving HP/stress). Original mode auto-saves to the DB.
- **Scene detail**: Same pencil → choice dialog → modal flow. Copy mode converts the reference to an inline owned copy in the parent scene. Original mode saves to the DB.
- SRD and public items are always forced into copy mode.

Scenes store their elements as either library ID references or inline **owned copies**. Owned copies appear with an amber "local copy" badge and are preserved through normal edit/save operations.

## Supabase Setup (Database)

### 1. Create a project

1. Go to [supabase.com](https://supabase.com) and create a new project.
2. Choose a region close to your users and set a strong database password.

### 2. Get the connection string

1. Supabase dashboard → **Project settings** → **Database**.
2. Under **Connection string**, select **URI** and copy the string.
3. Replace `[YOUR-PASSWORD]` with your database password and paste it into `.env`:

```env
DATABASE_URL=postgresql://postgres:[YOUR-PASSWORD]@db.xxxxxxxxxxxx.supabase.co:5432/postgres
```

> **Tip:** For serverless/edge environments use the **Session pooler** (port 5432) or **Transaction pooler** (port 6543) connection strings instead of the direct connection.

### 3. Enable Supabase Storage for battle map images (optional)

Battle map images uploaded by the GM are stored in Supabase Storage so they are served from the CDN rather than embedded as data URLs in `table_state`. This step is optional — without it the map still works, but images are stored as data URLs which can make `table_state` saves large.

1. Supabase dashboard → **Storage** → **New bucket**.
2. Name it **`whiteboard-assets`** and enable **Public bucket** (so images can be served directly without signed URLs).
3. Supabase dashboard → **Project settings** → **API**.
4. Copy the **Project URL** and the **`service_role`** secret key (under "Project API keys").
5. Add to `.env`:

```env
SUPABASE_URL=https://xxxxxxxxxxxx.supabase.co
SUPABASE_SERVICE_ROLE_KEY=<service_role_key>
```

### Overnight V2 Feature Agents

`npm run agents` launches parallel [Cursor Cloud Agents](https://cursor.com/dashboard/cloud-agents) that implement and validate V2 features overnight against your GitHub repo. Agents run in Cursor's cloud — your machine can sleep.

```bash
# Prerequisites: CURSOR_API_KEY in .env (create at https://cursor.com/dashboard/cloud-agents)
# Optional for PR creation (val/unblock): GITHUB_TOKEN or GH_TOKEN in .env (fine-grained PAT with repo scope)

caffeinate -i npm run agents -- --agents 3          # 3 parallel agents, prevent Mac sleep
npm run agents -- --agents 5 --model claude-4.6-opus-high-thinking  # explicit model
npm run agents -- --impl-only                        # implement only (skip validation rounds)
npm run agents -- --val-only                         # validate only
```

The orchestrator alternates impl and val rounds, merging each round's branches back to `main` before starting the next. When all autonomous work is done it prints a **Waiting for Human** report listing any `Needs Fix` and `Blocked` items for you to address with `"Fix features"` or `"Unblock features"` in a Cursor chat.

**Regression test policy**: every bugfix must include a test that fails without the fix and passes with it. See `.cursor/rules/testing.mdc` for detailed guidance, including how to mock Firebase auth and assert CSS properties for visual bug regressions.

The Playwright test server runs on port 3457 (`NODE_ENV=test`) with a Firebase auth bypass for `Authorization: Bearer test-token`. The `test/helpers/auth.js` helper sets up all required route mocks in one call for single-actor tests.

**Multi-actor tests** (T12): `test/helpers/multi-auth.js` supports 2+ concurrent authenticated identities hitting the **real** server (no route mocking beyond Firebase CDN + `/api/config`). Uses `Bearer test-token:<uid>:<email>` tokens (multi-identity `requireAuth` extension, active only under `NODE_ENV=test`). `test/browser/action-loop-multi-actor.spec.js` covers M1 (roll SSE propagation + element-update SSE), M3 (rest cycle SSE), and M6 (token-position SSE to multiple clients). Requires a real Postgres (`DATABASE_URL`) for the full suite; basic auth extension tests run without DB. Playwright `globalSetup` (`test/playwright-global-setup.js` / `cleanupOrphanedTestTables`) purges leftover `table_state` rows for `test-user-uid*` before each browser/subclass suite so orphaned nav tabs (e.g. "T12 Test Table") do not accumulate across interrupted runs.

**Subclass feature video suite** (opt-in, **not** part of `npm test`/`test:browser`/CI): `npm run test:subclasses` runs `test/browser-subclass/*.spec.js` (Playwright project `subclass-videos`, parallel via `SUBCLASS_PARALLEL=1`; override with `SUBCLASS_WORKERS`); `npm run test:subclass -- <filter>` runs one matching spec serially (e.g. `bard-troubadour`). One test per subclass drives every feature it grants across GM / Player A / optional Player B contexts and stitches a multi-camera director `.webm` (hard cuts from caption roles; **active-camera-only** screencast to keep parallel headed runs stable; system `ffmpeg` required) to `test-artifacts/subclass-videos/` (gitignored, most-recent-run-only). Runs **headed** by default so WebGL dice appear (`SUBCLASS_HEADED=0` for headless); only the active stitch camera shows dice / records. Per-worker GM/player uids keep banner queues isolated. See `test/subclass-video-test-plan.md` for the coverage tracker and harness usage notes.

**CI**: both suites run automatically on every push and pull request via `.github/workflows/ci.yml` (Node 22 LTS, `npm ci`, `npm run build`, then `npm run test:unit` followed by `npm run test:browser`). No secrets required — Firebase is mocked in tests and the server runs without `DATABASE_URL`.

### Deployment (Railway)

A `Dockerfile` is included; Railway builds and runs it directly with no extra config file needed.

1. Create a new Railway project and connect this GitHub repo (or run `railway init` + `railway up` from the CLI). Railway auto-detects the `Dockerfile` and builds from it.
2. Add a Postgres database (Railway's built-in Postgres plugin works, or point `DATABASE_URL` at Supabase/any external Postgres).
3. Set the required environment variables in the Railway project's Variables tab (or via `railway variables --set KEY=value`):
   ```
   DATABASE_URL=...
   FIREBASE_PROJECT_ID=...
   FIREBASE_API_KEY=...
   FIREBASE_AUTH_DOMAIN=...
   FIREBASE_APP_ID=...
   APP_ID=...
   ADMIN_EMAILS=...
   QA_EMAILS=...
   ```
4. Deploy — pushes to the connected branch (or `railway up`) trigger a build + deploy automatically.

The Dockerfile clones the `daggerheart-srd` submodule during the build if the build context didn't already include it (common on Railway, since it builds from a tarball of the repo rather than a full git clone).
